# 로딩 / 성능 보고서 (느린 폰, 느린 인터넷)

목표: **아주 느린 인터넷과 오래된 폰에서도 게임 도중에 그림을 기다리느라 멈추지 않게 하기.** 그래서 게임을 열 때 그림을 전부 먼저 받아 두고, 한 번 받은 그림은 폰에 저장해서 다음부터는 인터넷 없이 열리게 했어.

## 1. 결과 한눈에

같은 조건에서 예전(main)과 지금을 같은 자동 플레이 봇으로 쟀어. 조건은 **인터넷 60KB/s(약 0.5Mbps), 요청마다 지연 0.5초, 폰 CPU 4배 느리게, 화면을 빠르게 연타(0.15초마다)**야.

| | 예전 | 지금 (처음 방문) | 지금 (다시 방문) |
|---|---|---|---|
| 게임을 시작할 수 있게 되기까지 | 24.7초 | 155초 (그림 9MB를 다 받는 시간) | 2.3초 |
| 플레이 중 그림 기다리느라 멈춘 횟수 (6판) | 9번 | 3번 | 3번 |
| 멈춘 시간 합계 | 33.4초 | 0.4초 | 0.25초 |
| 가장 길게 멈춘 시간 | 4.0초 (대기 한도에 걸림) | 0.15초 | 0.15초 |
| 다시 방문했을 때 새로 받은 그림 | - | - | 0바이트 (요청 0개) |

- 처음 방문의 155초는 인터넷 속도 한계야. 그림이 전부 합쳐 약 9MB라서 60KB/s면 150초가 걸려. 대신 **처음 한 번만** 받아.
- "멈춘 횟수"는 그림을 여는 데 걸린 0.15초 정도의 짧은 대기야. 그림을 못 받아서 멈춘 게 아니야.
- 인터넷 속도가 150KB/s(보통 느린 4G)일 때는 처음 방문이 약 60초야.

## 2. 무엇을 바꿨나

### 새 파일
- `sw.js` (서비스 워커): 그림을 폰 저장소에 두고 꺼내 주는 일을 해.
  - `images/` 아래 그림은 저장소에 있으면 인터넷에 안 가고 바로 줘.
  - 게임 페이지(`index.html`)는 인터넷을 먼저 시도하되, 3초 안에 안 오면 저장해 둔 걸 보여줘. (서버 응답이 8초 걸리는 상황에서 재방문이 3.3초에 열려. 저장본이 없으면 약 18초)
  - 서버의 그림이 바뀌었는지는 6시간에 한 번 뒤에서 하나씩 물어봐 (ETag). 안 바뀐 건 본문 0바이트라 거의 공짜야. 바뀐 그림만 새로 받아서 **다음 접속부터** 새 그림이 나와.
- `head.html`: 첫 화면(어두운 배경에 "귤복복 살인사건 / 게임을 불러오는 중…"). 페이지 파일이 다 오기 전에 하얀 화면 대신 나와. 내용은 `index.html`의 `<head>` 끝에 이미 들어 있어. **Tweego 로 다시 빌드할 때 `--head=head.html` 을 붙여야 들어가.** 안 붙이면 이 첫 화면만 빠지고 게임은 그대로 돌아가.
- `tools/`: 검사와 시험 도구 (`tools/README.md`).

### `StoryScript` (twee 와 index.html 양쪽에 같은 내용)
- **그림 전부 받기(`Dl`)**: 배경, 타이틀, 오프닝 인물, 용의자 루트 첫 인물, 나머지 인물, 엔딩 순서로 전부 받아. 받을 목록은 `CHAR` 표와 `ENDING_FILES` 표에서 읽으니까 그림을 추가해도 이 코드는 안 고쳐도 돼.
  - 동시에 4개씩 받아 (지연이 큰 회선에서 놀지 않게).
  - 파일 하나가 15초 동안 한 바이트도 안 오면 끊고 다시 받아. 최대 6번, 간격은 0.7초부터 점점 늘어나.
  - 인터넷이 끊기면 연결될 때까지 기다리고, 받다가 닫아도 다음에 이어서 받아.
  - 받는 중에 폰 화면이 꺼지면 받기가 멈추니까, 화면 꺼짐 방지를 켜 (지원하는 브라우저만).
- **로딩 화면**: 퍼센트, 받은 양 / 전체(MB), 남은 시간 어림, 데이터 안내를 보여줘. 20초가 넘게 걸리면 `먼저 시작하기 (중간에 끊길 수 있어요)` 버튼이 나와. 못 받은 그림이 있으면 `다시 받기` 버튼이 나와. 이미 다 받아 둔 사람에게는 로딩 화면이 거의 안 보여.
- **인물 그림 열어 두기(디코딩)**: 예전에는 29명 + 표정을 전부 뒤에서 열었는데, 이제는 오프닝 인물과 용의자 루트 첫 인물 16명만 뒤에서 한 장씩 천천히 열고, 나머지는 장면 미리보기(4장면 앞)가 열어. 크로미엄 실측으로 메모리가 줄고 끊김은 그대로 0이야 (4번 항목).
- **엔딩 그림**: 엔딩이 나오기 전에 그림이 아직 안 왔으면 그 그림을 맨 앞으로 당겨서 받아. 기다리는 한도를 3초에서 8초로 늘렸어.
- **대사 시작 전에 그림 기다리는 한도**: 4초에서 10초로 늘렸어. 한도에 걸리면 그림 없이 대사가 먼저 나오던 걸 줄이려는 거야. 그림이 아예 못 받아지면 바로 넘어가.

## 3. 안 바뀐 것
- 스토리, 대사, 선택지, 엔딩, `CHAR` / `PAIR` / `ENDING_FILES` 표, 그림 파일은 하나도 안 건드렸어.
- 그림 파일의 용량 / 화질도 그대로야 (자르거나 줄이지 않음).
- `file://` 로 내 컴퓨터에서 열 때는 그림을 미리 받는 일을 안 하고, 예전처럼 폴더에서 바로 읽어.

## 4. 시험한 것과 결과 (자동 시험 도구: `tools/perf/`)

| 시험 | 결과 |
|---|---|
| 60KB/s + 지연 0.5초 + CPU 4배, 6판 플레이 | 위 표 |
| 처음 받다가 35% 확률로 연결이 끊김 | 15번 끊겼지만 48개 파일 전부 받음, 로딩 15초, 에러 0 |
| 연결은 살아 있는데 데이터가 멈춤 (20% 확률) | 14번 멈췄고 15초 뒤 끊고 다시 받아서 전부 받음 (67초) |
| 한 번 받은 뒤 **서버를 꺼 놓고** 다시 열기 | 0.2초에 열리고 대사 장면까지 정상 진행, 에러 0 |
| 서버 응답이 8초 걸리는 상태에서 다시 열기 | 3.3초에 열림 |
| 서버의 그림 1개를 바꿈 | 48개 중 47개는 304(안 바뀜), 바뀐 1개만 새로 받음 |
| 서비스 워커를 못 쓰는 브라우저 (대체 경로) | 처음에 다 받고 거의 안 끊김 (끊김 2번, 0.27초), 다시 열면 기본 캐시로 5초 |
| `먼저 시작하기` 를 25초에 눌렀을 때 | 예전 수준으로 끊김 (9번, 34초). 버튼에 경고가 적혀 있는 이유야 |
| 메모리 (크로미엄 렌더러 RSS, 10판 플레이 뒤) | 예전 562MB / 지금 540MB / 29명 전부 열기 606MB / 안 열기 516MB. 데스크톱 값이라 절대값은 참고용이고 비교만 의미 있어 |

메모리에서 알게 된 것: **열어 둔 그림을 오래된 것부터 버리는 방식은 오히려 메모리를 늘렸어** (3장만 유지 661MB, 10장 607MB, 제한 없음 519MB). 버렸다가 다시 열 때 낭비가 더 컸어. 그래서 버리기는 넣지 않았어.

## 5. 한계와 주의
- 실제 폰(특히 iOS 사파리)에서는 아직 못 재 봤어. 위 숫자는 크로미엄 + 인터넷 / CPU 느리게 흉내 낸 값이야.
- **처음 방문은 약 9MB를 받아야 해.** 아주 느린 회선에서는 몇 분이 걸려. 그래서 로딩 화면에 받은 양, 남은 시간, 데이터 사용 안내를 보여줘.
- 폰 브라우저가 저장 공간이 모자라서 저장해 둔 그림을 지우면, 다음 접속 때 다시 받아.
- 같은 이름으로 그림을 덮어쓴 경우, 이미 받아 둔 사람은 최대 6시간 뒤 접속부터 새 그림이 나와 (그 사이 접속에서 뒤에서 확인하고 바꿔 둠). 바로 보고 싶으면 주소 뒤에 `?nosw` 를 붙여 열면 저장해 둔 것을 전부 지우고 평소처럼 받아. 화면이 이상할 때도 같은 방법으로 풀려.
- `sw.js` 를 고치면 안의 `SW_VERSION` 을 올려야 해. 그때 `index.html` 안의 `SW_IMG_CACHE`(예: `bokbok-img-v1`)도 같은 숫자로 맞춰.
- `먼저 시작하기` 버튼이 필요 없으면 `SKIP_AFTER_MS` 를 아주 큰 숫자로 바꾸면 안 나와.

## 6. 앞으로 더 줄이고 싶다면 (아직 안 한 것)
- 용량 자체를 줄이는 방법: 그림 아래쪽 약 30%는 대사창에 가려져. 잘라서 쓰면 용량과 메모리가 약 30% 줄어들어. 다만 대사창이 78% 불투명이라 아래쪽이 아주 흐리게 비쳐 보여서, 자르면 그림이 조금 달라 보일 수 있어. 눈 위치 값(`CHAR`)도 다시 맞춰야 해서 캐릭터 이미지 담당과 같이 정해야 해.
- 포포(2000×2000)만 1600×1600 으로 줄이기 (한 장에 약 16MB → 10MB).
